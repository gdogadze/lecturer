DevOps და CI/CD

გასულ კვირას პროგრამა თქვენს მანქანაზე გაეშვა. დღეს იმას დაამატებთ, რომ ყოველი ცვლილება თავად იწყობა და თავად მოწმდება.

კურსი წინა: .NET ცნობარი: CI

სილაბუსის ამ კვირის შედეგი ერთი ჩვევაა. გუნდის კოდი საერთო საცავში შედის, და იქვე ეშვება აწყობა, ტესტი და სტილის შემოწმება. GitHub Actions, Azure Pipelines და Jenkins სამი მასპინძელია ერთი და იმავე საქმისთვის.

ლექტორისთვის · გახსნა, დაახლოებით 5 წუთი

წინაპირობაა გასული ლაბორატორია: dotnet run მუშაობს. თუ ვინმეს SDK არ დგას, დღევანდელი საათი იქ ჩერდება. Git-ის სრულ კურსს ნუ დაიწყებთ. საკმარისია: საცავი, commit, push. დეპლოის დღეს არ ვაკეთებთ. Cloud მე-6 კვირაა.

01რატომ მოწმდება ყოველი ცვლილება

ადამიანი ხშირად დიდხანს წერს საკუთარ ტოტში და ბოლოს აერთიანებს. მაშინ კონფლიქტი, გატეხილი აწყობა და ორმაგი სამუშაო ერთად მოდის. Continuous integration ამას წინ ეწევა: საერთო კოდში შესული ყოველი ცვლილება აწყობას და ტესტს იწვევს.

Microsoft-ის განმარტებით, CI არის ავტომატური აწყობა და ტესტი ყოველ ჯერზე, როცა კოდი საცავში შედის. შეცდომა იმ დღეს ჩანს, როცა ის დაიწერა. ერთი კვირის შემდეგ იმავე შეცდომის პოვნა ძვირია, იმიტომ რომ ავტორს უკვე აღარ ახსოვს, რატომ შეცვალა ის სტრიქონი.

02სამი ნაბიჯი, ერთი ფაილი

GitHub-ზე ამ ფაილს workflow ჰქვია. ის დგას .github/workflows/ საქაღალდეში და YAML-ია. გაშვებულ პროცესს pipeline ჰქვია. ფაილი აღწერს, გაშვება ასრულებს.

workflow შედგება job-ებისგან. job შედგება step-ებისგან. დღევანდელ ლაბორატორიას ერთი job ყოფნის. სამი ნაბიჯი საკმარისია.

  1. actions/checkout საცავის კოდს მოაქვს მანქანაზე, რომელიც აწყობას გაუშვებს. ამ მანქანას runner ჰქვია.
  2. actions/setup-dotnet მითითებულ SDK-ს აყენებს. runner-ზე შეიძლება სხვა ვერსია უკვე იდგეს. ჩვენ 10.0.x-ს ვეუბნებით, რომ ლაბორატორია და სერვერი ერთ პლატფორმაზე იდგეს.
  3. dotnet test აღადგენს პაკეტებს, აწყობს და ტესტს გაუშვებს. თუ ტესტი წითელია, ნაბიჯი წითელია და pipeline წითელია.
name: build and test

on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-dotnet@v6
        with:
          dotnet-version: "10.0.x"
      - run: dotnet test --configuration Release

on: [push, pull_request] ნიშნავს: ეშვება, როცა კოდი შედის, და მაშინაც, როცა ვინმე შერწყმას სთხოვს. ubuntu-latest Linux-ის runner-ია. იგივე ბრძანება თქვენს Windows-ზეც და Mac-ზეც მუშაობს. ამიტომ გასული კვირის პლატფორმა დღეს გამოგვადგება.

ფაილის ადგილი და ნაბიჯების ფორმა: Building and testing .NET. იქაური მაგალითები ძველ ვერსიებზე დგას. დღევანდელი ნომრები აქედანაა: setup-dotnet README, checkout@v7 და setup-dotnet@v6.

GitHub Actions-ის ფაილი სად დგას?

დააჭირეთ იმ რიგით, რომლითაც runner მუშაობს

არასწორ ნაბიჯს ლოგი გეტყვით, რატომ გატყდა. სწორი რიგის შემდეგ დააჭირეთ „თავიდან“, თუ კიდევ გინდათ.

    04ტესტი და სტილის შემოწმება

    ტესტი არის პატარა პროგრამა, რომელიც თქვენს კოდს იძახებს და პასუხს ადარებს. xUnit-ში ერთ შემოწმებას [Fact] ეწოდება. Assert.Equal წითელდება, თუ რიცხვები არ ემთხვევა. მაშინ dotnet test ნულს არ აბრუნებს, და pipeline-იც წითელდება.

    public class GradesTests
{
    [Fact]
    public void Sum_adds_three_scores()
    {
        int[] scores = [10, 9, 8];
        Assert.Equal(27, Grades.Sum(scores));
    }
}

    ფრჩხილები გასული კვირისაა. ტესტი ახალ თემას ძველ ფორმაში დებს, რომ C# 12 ცალკე თავად არ დარჩეს.

    მეორე შემოწმება სტილია. dotnet format --verify-no-changes ფაილს არ ცვლის. თუ ფორმატერი რამეს შეცვლიდა, ბრძანება შეცდომით სრულდება. pipeline-ში ეს ნაბიჯი ნიშნავს: საცავში შევიდა კოდი, რომელიც შეთანხმებულ ჩანაწერს არ ემთხვევა. წესები .editorconfig-იდან იკითხება. ფაილის გარეშე მოქმედებს ნაგულისხმევი წესები.

    Roslyn-ის ანალიზატორები კომპილაციის დროს გაფრთხილებას წერენ. მათი სრული კატალოგი დღეს არ გვჭირდება. საკმარისია იცოდეთ, რომ ხარისხის შემოწმება ორი სახისაა: ტესტი ამოწმებს პასუხს, ფორმატერი ამოწმებს ჩანაწერს. ორივე შეიძლება წითელ ნაბიჯად იქცეს.

    05CD ერთი ნაბიჯით შორსაა

    Continuous delivery იგივე ჯაჭვს აგრძელებს. აწყობა, რომელმაც ტესტი გაიარა, მიდის გარემოში: ჯერ საცდელში, მერე პროდაქშენში. Microsoft ამას ასე ყოფს: CI იწყებს, გამოშვების pipeline კი გარემოდან გარემოზე გადააქვს, ყოველ გარემოზე თავისი შემოწმებით.

    დღევანდელ ლაბორატორიაში გარემო არ გვაქვს. dotnet publish არის ბრძანება, რომელიც გასაშვებ ფაილებს კრებს. სად აღწევს ის ფაილები, Azure-ში თუ სხვაგან, მე-6 და მე-7 კვირის თემაა. დღეს pipeline მწვანეა მაშინ, როცა ტესტი მწვანეა.

    06ლაბორატორია

    ერთი საათი. ბოლოს dotnet test მწვანეა, workflow კი საცავში დგას. სერვერზე არაფერს ვტვირთავთ.

    mkdir GradeBook && cd GradeBook
dotnet new sln -n GradeBook
dotnet new classlib -n GradeBook -f net10.0
dotnet new xunit -n GradeBook.Tests -f net10.0
dotnet sln add GradeBook/GradeBook.csproj
dotnet sln add GradeBook.Tests/GradeBook.Tests.csproj
dotnet add GradeBook.Tests reference GradeBook

    თუ SDK 8-ია, ორივე -f ჩაანაცვლეთ net8.0-ით. კოდი C# 12-ია და იქაც იგება.

    GradeBook/Grades.cs ჩაანაცვლეთ ამით. შაბლონის Class1.cs წაშალეთ.

    public static class Grades
{
    public static int Sum(int[] scores)
    {
        int total = 0;
        foreach (int score in scores)
            total += score;
        return total;
    }
}

    GradeBook.Tests/GradesTests.cs ჩაანაცვლეთ ზემოთ მოყვანილი ტესტით. შაბლონის UnitTest1.cs წაშალეთ, თორემ ცარიელი ტესტიც გაეშვება და სურათს აერევა.

    გაუშვით dotnet test. ელოდებიან ერთ გამვლელ ტესტს. მერე Assert.Equal-ში 27 ჩაანაცვლეთ 99-ით, ისევ გაუშვით, და წითელი წაიკითხეთ. დააბრუნეთ 27. ეს წითელი არის ის, რასაც pipeline დაგიმალავთ, თუ ტესტი საცავში არ დგას.

    workflow, სანამ GitHub-ზე ატვირთავთ

    ჩასვით თქვენი YAML. შემმოწმებელი GitHub არ არის. ის ოთხ ნიშანს ეძებს.

      სახლში
