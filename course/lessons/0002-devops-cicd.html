DevOps და CI/CD

გასულ კვირას პროგრამა თქვენს მანქანაზე გაეშვა. დღეს დაამატებთ ავტომატიზაციას: ყოველი ცვლილება თავისით აიწყობა და შემოწმდება.

კურსი წინა: .NET ცნობარი: CI

სილაბუსის ამ კვირის შედეგი ერთი ჩვევაა: გუნდის კოდი საერთო საცავში შედის და იქვე ეშვება აწყობა, ტესტირება და სტილის შემოწმება. GitHub Actions, Azure Pipelines და Jenkins სამი სხვადასხვა სისტემაა ერთი და იმავე საქმისთვის.

ლექტორისთვის · გახსნა, დაახლოებით 5 წუთი

წინაპირობაა გასული ლაბორატორია: dotnet run მუშაობს. თუ ვინმეს SDK არ აქვს დაყენებული, მისთვის დღევანდელი საათი იქვე წყდება. Git-ის სრულ კურსს ნუ დაიწყებთ. საკმარისია: საცავი, commit, push. დეპლოის დღეს არ ვაკეთებთ. Cloud მე-6 კვირის თემაა.

01რატომ მოწმდება ყოველი ცვლილება

დეველოპერი ხშირად დიდხანს მუშაობს საკუთარ ბრენჩზე და ბოლოს აერთიანებს. მაშინ კონფლიქტები, გაფუჭებული აწყობა და ორმაგი სამუშაო ერთდროულად ჩნდება. Continuous integration ამას თავიდან გვაცილებს: საერთო კოდში შეტანილი ყოველი ცვლილება იწვევს აწყობასა და ტესტირებას.

Microsoft-ის განმარტებით, CI არის ავტომატური აწყობა და ტესტი ყოველ ჯერზე, როცა კოდი საცავში შედის. შეცდომა იმავე დღეს ჩანს, როცა დაიწერა. ერთი კვირის შემდეგ შეცდომის პოვნა ძვირი ჯდება, რადგან ავტორს აღარ ახსოვს, რატომ შეცვალა ეს სტრიქონი.

02სამი ნაბიჯი, ერთი ფაილი

GitHub-ზე ამ ფაილს workflow ჰქვია. ის დგას .github/workflows/ საქაღალდეში და YAML-ია. გაშვებულ პროცესს pipeline ჰქვია. ფაილი აღწერს, გაშვება ასრულებს.

workflow შედგება job-ებისგან. job შედგება step-ებისგან. დღევანდელ ლაბორატორიას ერთი job ყოფნის. სამი ნაბიჯი საკმარისია.

  1. actions/checkout საცავის კოდს იმ მანქანაზე ჩამოიტანს, რომელიც აწყობას გაუშვებს. ამ მანქანას runner ჰქვია.
  2. actions/setup-dotnet მითითებულ SDK-ს აყენებს. runner-ზე შეიძლება სხვა ვერსია უკვე იყოს დაყენებული. ჩვენ ვთხოვთ 10.0.x-ს, რომ ლაბორატორიაც და სერვერიც ერთსა და იმავე ვერსიაზე მუშაობდეს.
  3. dotnet test აღადგენს პაკეტებს, აწყობს პროექტს და უშვებს ტესტებს. თუ ტესტი ჩავარდა, ნაბიჯიც და pipeline-იც წითლდება.
name: build and test

on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-dotnet@v6
        with:
          dotnet-version: "10.0.x"
      - run: dotnet test --configuration Release

on: [push, pull_request] ნიშნავს: ეშვება, როცა კოდი იგზავნება (push), და მაშინაც, როცა ვინმე შერწყმას ითხოვს (pull request). ubuntu-latest Linux-ის runner-ია. იგივე ბრძანება თქვენს Windows-ზეც და Mac-ზეც მუშაობს. ამიტომ გასულ კვირას შესწავლილი პლატფორმა დღესაც გამოგვადგება.

ფაილის ადგილი და ნაბიჯების ფორმა: Building and testing .NET. იქაური მაგალითები ძველ ვერსიებს იყენებს. დღევანდელი ნომრები აქედანაა: setup-dotnet README, checkout@v7 და setup-dotnet@v6.

GitHub Actions-ის ფაილი სად დგას?

დააჭირეთ იმ თანმიმდევრობით, რომლითაც runner მუშაობს

არასწორი ნაბიჯის შემთხვევაში ლოგი გეტყვით, რატომ ჩავარდა. სწორი თანმიმდევრობის პოვნის შემდეგ, თუ გსურთ, დააჭირეთ „თავიდან“.

    03სამი სისტემა, იგივე ბრძანება

    სილაბუსში სამი ინსტრუმენტია დასახელებული. ლაბორატორიაში ერთით, GitHub Actions-ით, ვიმუშავებთ, რადგან ანგარიში უფასოა და ფაილი საცავში ინახება. დანარჩენი ორიც იგივე dotnet test-ს უშვებს, ოღონდ სხვა ფაილიდან.

    04ტესტი და სტილის შემოწმება

    ტესტი პატარა პროგრამაა, რომელიც თქვენს კოდს იძახებს და შედეგს მოსალოდნელ მნიშვნელობას ადარებს. xUnit-ში ერთ ტესტურ შემთხვევას [Fact] აღნიშნავს. Assert.Equal ვარდება, თუ მნიშვნელობები არ ემთხვევა. მაშინ dotnet test ნულისგან განსხვავებულ კოდს აბრუნებს და pipeline-იც წითლდება.

    public class GradesTests
{
    [Fact]
    public void Sum_adds_three_scores()
    {
        int[] scores = [10, 9, 8];
        Assert.Equal(27, Grades.Sum(scores));
    }
}

    კვადრატული ფრჩხილები გასული კვირიდანაა. ტესტი ახალ თემას ნაცნობ ფორმაში გვაჩვენებს, რომ C# 12 ცალკე თემად არ დარჩეს.

    მეორე შემოწმება კოდის სტილია. dotnet format --verify-no-changes ფაილებს არ ცვლის. თუ ფორმატერი რამეს შეცვლიდა, ბრძანება შეცდომით სრულდება. pipeline-ში წითელი ნაბიჯი ნიშნავს, რომ საცავში შევიდა კოდი, რომელიც შეთანხმებულ სტილს არ შეესაბამება. წესები .editorconfig ფაილიდან იკითხება; თუ ის არ არსებობს, ნაგულისხმევი წესები გამოიყენება.

    Roslyn-ის ანალიზატორები კომპილაციისას გაფრთხილებებს გვაძლევენ. მათი სრული კატალოგი დღეს არ გვჭირდება. საკმარისია იცოდეთ, რომ ხარისხის შემოწმება ორი სახისაა: ტესტი შედეგს ამოწმებს, ფორმატერი კი კოდის ჩაწერის სტილს. ორივე შეიძლება წითელ ნაბიჯად იქცეს.

    dotnet format.

    05CD ერთი ნაბიჯით წინაა

    Continuous delivery იმავე ჯაჭვს აგრძელებს. აწყობა, რომელმაც ტესტები გაიარა, გადადის გარემოებში: ჯერ სატესტოში, შემდეგ პროდაქშენში. Microsoft ამას ასე ანაწილებს: CI პროცესს იწყებს, გამოშვების pipeline კი აწყობას ერთი გარემოდან მეორეში გადაიტანს და თითოეულ გარემოში საკუთარ შემოწმებას ატარებს.

    დღევანდელ ლაბორატორიაში გარემო არ გვაქვს. dotnet publish ბრძანებაა, რომელიც გასაშვებ ფაილებს აგროვებს. სად გადავა ეს ფაილები, Azure-ში თუ სხვაგან, მე-6 და მე-7 კვირის თემაა. დღეს pipeline მწვანეა, როცა ტესტები მწვანეა.

    06ლაბორატორია

    ერთი საათი. ბოლოს dotnet test მწვანე უნდა იყოს, workflow-ის ფაილი კი საცავში უნდა იდოს. სერვერზე არაფერს ვტვირთავთ.

    mkdir GradeBook && cd GradeBook
dotnet new sln -n GradeBook
dotnet new classlib -n GradeBook -f net10.0
dotnet new xunit -n GradeBook.Tests -f net10.0
dotnet sln add GradeBook/GradeBook.csproj
dotnet sln add GradeBook.Tests/GradeBook.Tests.csproj
dotnet add GradeBook.Tests reference GradeBook

    თუ SDK 8-ია, ორივე -f ჩაანაცვლეთ net8.0-ით. კოდი C# 12-ია და იქაც იგება.

    GradeBook/Grades.cs-ის შიგთავსი ჩაანაცვლეთ ამით. შაბლონის Class1.cs წაშალეთ.

    public static class Grades
{
    public static int Sum(int[] scores)
    {
        int total = 0;
        foreach (int score in scores)
            total += score;
        return total;
    }
}

    GradeBook.Tests/GradesTests.cs-ის შიგთავსი ჩაანაცვლეთ ზემოთ მოყვანილი ტესტით. შაბლონის UnitTest1.cs წაშალეთ, თორემ ცარიელი ტესტიც გაეშვება და შედეგს დააბნევს.

    გაუშვით dotnet test. მოსალოდნელია ერთი გავლილი ტესტი. შემდეგ Assert.Equal-ში 27 შეცვალეთ 99-ით, ისევ გაუშვით და წაიკითხეთ წითელი შეტყობინება. დააბრუნეთ 27. ამ წითელ შედეგს ვერ დაინახავდით, თუ ტესტი საცავში არ იქნებოდა.

    workflow-ის შემოწმება GitHub-ზე ატვირთვამდე

    ჩასვით თქვენი YAML. ეს შემმოწმებელი GitHub არ არის, ის მხოლოდ ოთხ ნიშანს ეძებს.

      სახლში

      1. დაამატეთ მეორე [Fact]: ცარიელი მასივის ჯამი 0-ის ტოლია.
      2. დარწმუნდით, რომ Sum ცარიელ მასივზეც სწორად მუშაობს და ტესტი მწვანე რჩება. არსებული კოდი ამას უკვე აკეთებს, მაგრამ ტესტმა ეს აშკარად უნდა დაადასტუროს.
      3. workflow-ში, dotnet test-ის წინ, დაამატეთ ნაბიჯი dotnet format --verify-no-changes.

      თუ GitHub-ის ანგარიში არ გაქვთ, ლაბორატორიაზე მოიტანეთ მწვანე dotnet test და YAML ფაილი. ანგარიშის გარეშე runner ვერ გაეშვება, მაგრამ ლოკალური ტესტი მაინც თქვენი შედეგია.

      07ოთხი წინადადება

      1. CI ყოველ ცვლილებაზე აწყობს და ამოწმებს.
      2. GitHub-ზე ეს ფაილი .github/workflows-შია. Azure-ში azure-pipelines.yml-ია. Jenkins-ში Jenkinsfile-ია.
      3. სამივეში ბრძანება ერთია: dotnet test.
      4. CD შემოწმებულ აწყობას გარემოში აგზავნის. დღეს ამ ეტაპამდე არ მივდივართ.

      შემდეგი კვირა არქიტექტურაა: SOLID, MVC და დამოკიდებულების ინექცია (dependency injection). რუკა ერთ გვერდზე: ცნობარი. გასული კვირა: ეკოსისტემა.

      წაიკითხეთ პირველადი წყარო

      ლაბორატორიის წყარო არის Building and testing .NET. ვერსიები კი setup-dotnet-ის README-დან აიღეთ, რადგან სახელმძღვანელოს მაგალითი ძველ SDK-ს იყენებს. განმარტებისთვის: What is continuous integration.

      თუ pipeline გატყდა და ამ გვერდზე მიზეზი არ ჩანს, წაიკითხეთ წითელი ლოგი და კითხვა დასვით r/dotnet-ზე ან Microsoft Q&A-ზე. ლოგის გარეშე დასმულ კითხვას პასუხი არ ექნება.

      ლექტორო, თუ დარბაზში კითხვა გაჩნდა და ამ გვერდზე პასუხი არ დგას, მომწერეთ ჩატში. სტუდენტის ფორმულირებაც მოიტანეთ. შემდეგ გაკვეთილს მის საფუძველზე ავაგებთ.
