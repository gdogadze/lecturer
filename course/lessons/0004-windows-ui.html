Windows აპლიკაციები

კურსი წინა: SOLID ცნობარი: ფანჯარა

Windows აპლიკაციების განვითარება: WinUI, WPF, MAUI. WinForms და WPF-ის შედარება, MAUI-ს შესაძლებლობები, Fluent Design System და UWP თანამედროვე დიზაინში.

ერთი და იგივე ფანჯარა რამდენიმე ფრეიმვორკით იწერება. დღეს თითოეულს ცალკე გავდივართ. რას აკეთებს კარგად, სად აქვს საზღვარი, და რომელი ცნობილი პროგრამა დგას მასზე.

პროექტს დღეს არ ვქმნით. WinUI, WPF და WinForms მხოლოდ Windows-ზე იგება, დარბაზში კი Mac-იც დგას. საათი არჩევანს ეთმობა.

ლექტორისთვის

მოდელი არის ეს ვიდეო. ჯერ სამი Windows-ის ფრეიმვორკი, მერე ვინ იყენებს, მერე კითხვები, რომლითაც გუნდი ირჩევს. „ასე არა“, ლაბორატორია და საშინაო ამ გვერდზე არ არის.

თუ საათი წაიწელა, წაიკითხეთ სამი ფრეიმვორკის ცხრილი და ბოლოს ოთხი კითხვა. Uno, Avalonia, React Native და PWA გამოტოვეთ. Fluent-ის ხუთი სახელი ერთ წინადადებაში დატოვეთ.

ვიდეო 2025 წლის მარტს ეკუთვნის და WinForms-ზე ამბობს, რომ მუქი რეჟიმი არ აქვს. .NET 10-ში Application.SetColorMode უკვე ჩვეულებრივი API-ა. მაინც თქვით საზღვარი. მუქი რეჟიმი Windows 11-ზეა, კონტრასტულ თემაში ითიშება, და სისტემის თემის შეცვლა გახსნილ აპს თავისით არ გადაჰყავს.

სახელები, რომლებიც დოკუმენტაციაში წერია და შეიძლება ხმამაღლა თქვათ: Microsoft Photos WinUI 3-ზეა, PowerToys-ის პარამეტრები და Command Palette WinUI 3-ზეა, Visual Studio-ს ინტერფეისის დიდი ნაწილი WPF-ა. სხვა პროდუქტი მეხსიერებიდან ნუ დაამატებთ.

01საიდან მოვიდა ეს სია

WinForms Visual Basic-ის ფორმების მემკვიდრეა და .NET-ის პირველი დესკტოპის ფანჯარა იყო. ეკრანს დიზაინერში აწყობდი, ღილაკს კი მეთოდი ჰქონდა.

WPF 2006 წელს გამოვიდა. ეს იყო Microsoft-ის პირველი XAML. XAML არის ტექსტური ფაილი, რომელიც ფანჯარას აღწერს, სანამ პროგრამა გაეშვება. ღილაკი, წარწერა, სტილი და მიბმა იმ ფაილში წერია.

2015 წელს Windows 10-თან ერთად მოვიდა UWP, Universal Windows Platform. იგივე აპი დესკტოპზე, Xbox-სა და HoloLens-ზე გადიოდა. მისი კონტროლების ბიბლიოთეკას WinUI 2 ჰქვია.

WinUI 3 იმავე XAML-ს Windows App SDK-ში დებს. განახლება ოპერაციული სისტემის ახალ ვერსიას აღარ ელოდება. MAUI 2022 წელს გამოვიდა, Xamarin.Forms-ის ადგილას, ერთი კოდით რამდენიმე სისტემისთვის.

გასულ კვირას MVVM-ში ხედი მოდელს კითხულობდა. XAML-ის binding, ქართულად მიბმა, სწორედ ის კითხვაა. წარწერა ViewModel-ის ველს მიჰყვება, და ველის შეცვლისას ეკრანი თავიდან იხატება. ღილაკის მეთოდს წარწერის სახელი აღარ სჭირდება.

02WinUI 3

ახალი ზოგადი Windows დესკტოპ აპისთვის Microsoft WinUI 3-ს ასახელებს. ის Windows App SDK-ის ფანჯარაა. namespace არის Microsoft.UI.Xaml. აპი მუშაობს Windows 10-ის ვერსია 1809-ზე და Windows 11-ზე, შეფუთულიც და შეუფუთავიც.

ენა არის C# ან C++. პროცესორი არის x86, x64 ან Arm. F# და Visual Basic ამ ფანჯარაში არ იწერება.

XAML-ში წერია სამი რამ, რაც ფორმის მეთოდს ცალკე კოდად მოჰქონდა. მიბმა წარწერას ველზე ამაგრებს. სტილი ზომას და ფერს ერთხელ აღწერს. რესურსი იმ სტილს სახელით ტვირთავს, ამიტომ ნარინჯისფერი თითოეულ წარწერაზე არ მეორდება.

<TextBlock Text="{x:Bind AverageText, Mode=OneWay}"
           Style="{StaticResource BodyTextBlockStyle}" />

{x:Bind} მიბმას აწყობის დროს ამოწმებს. ველს თუ სახელი გადაარქვი, პროექტი იგებს და შეცდომას მაშინ გიჩვენებს, როცა მომხმარებელს ცარიელი წარწერა ჯერ არ უნახავს. ჩვეულებრივი {Binding} იმ შეცდომას გაშვებისას წერს. {x:Bind} ნაგულისხმევად მნიშვნელობას ერთხელ კითხულობს. რომ წარწერა საშუალოს ცვლილებასაც მიჰყვეს, Mode=OneWay სჭირდება.

Visual Studio 2026-ში XAML Hot Reload განლაგებას და სტილს გაშვებულ აპში ცვლის. პროგრამა თავიდან არ ეშვება. WinUI 3-ს დიზაინერის ზედაპირი არ აქვს. ეკრანს Live Visual Tree-ში უყურებ, თვისებებს კი Live Property Explorer-ში.

დახატვა DirectX-ით მიდის, ამიტომ გრძელი სია და მოძრაობა გლუვია. სამი Windows-ის ფრეიმვორკიდან კალამს და შეხებას ყველაზე სრულად აქ იღებ.

Fluent Design System ამ კონტროლებს თან მოაქვს, Windows 10-ზეც და Windows 11-ზეც. ღია თემა, მუქი თემა და სისტემის აქცენტი აპს Windows-ის პარამეტრებიდან გადმოჰყვება. Mica Windows 11-ის მასალაა, ფონი სამუშაო მაგიდის ფერს ერევა. Windows 10-ზე ის ერთ ფერად ბრუნდება. Acrylic Windows 10 1809-ზეც მუშაობს. გამოყენებამდე კოდი ამოწმებს, მოწყობილობა იმ მასალას იღებს თუ არა.

Microsoft Photos ამ მოდელის საჯარო მაგალითია. აპი UWP-დან Windows App SDK-ზე გადავიდა და WinUI 3-ზე დარჩა. PowerToys-ის პარამეტრების ფანჯარა და Command Palette WinUI 3-ზეა აწყობილი. Windows-ის გარსის ნაწილი და ჩაშენებული აპებიც WinUI-ს იყენებს. კონტროლების სრული სია ცალკე აპში დევს, WinUI 3 Gallery, Microsoft Store-ში.

საზღვარი XAML-ის სწავლაა, თუ გუნდს აქამდე მხოლოდ ფორმის დიზაინერი უნახავს. მეორე საზღვარი ის არის, რომ UWP-ის პროექტში Windows App SDK არ იტვირთება. WinUI 2 და WinUI 3 ერთ პროექტში არ ჯდება, და გადასვლა მხოლოდ namespace-ის შეცვლა არ არის. ფანჯრის ძველი ტიპები, მაგალითად Window.Current, WinUI 3-ში აღარ დგას.

03WPF

WPF, Windows Presentation Foundation, ისევ მხოლოდ Windows-ზე იგება და ისევ მხარდაჭერილია. სამიზნე დღევანდელ .NET-ზეა, net10.0-windows. ეს .NET Framework-ის ძველი პროექტი არ არის.

ფანჯარა აქაც XAML-ია, ამიტომ მიბმა, სტილი და Hot Reload აქაც გაქვს. Visual Studio ცალკე ფანჯარაში აგროვებს binding-ის შეცდომებს, სანამ აპს აწყობ. დახატვა აქაც DirectX-ით მიდის, ამიტომ ტექსტი და ფორმა გადიდებაზე მკაფიო რჩება.

.NET 9-იდან WPF-ს Fluent თემა აქვს, და ის .NET 10-ზეც დარჩა. ჩართული თემა აპს Windows 11-ის იერს აძლევს, ღია რეჟიმით, მუქი რეჟიმით და სისტემის აქცენტის ფერით.

WPF-ს დიდი ბაზარი აქვს მზა კონტროლების. ცხრილი, დიაგრამა, ლენტი და რთული რედაქტორი წლებია იყიდება. თუ კონკრეტული კონტროლი WinUI-ში ჯერ არ არის, გუნდი ხშირად WPF-ზე რჩება სწორედ ამ ბაზრის გამო. იგივე გამყიდველები WinForms-ის კონტროლებსაც ყიდიან, ამიტომ ძველ ფორმასაც იშვიათად უწევს ღილაკის ნულიდან ხატვა.

Visual Studio-ს ინტერფეისის დიდი ნაწილი WPF-ა. დიდი პროგრამა, რომელსაც ეს ფრეიმვორკი დღესაც უძლებს.

ენა აქ C#-იც არის და Visual Basic-იც. ახალი ზოგადი აპის პირველი რჩევა მაინც WinUI 3-ია. თუ პროექტი უკვე WPF-ზეა დაწერილი, Microsoft მას იქ ტოვებს. გადატანა მაშინ იწყება, როცა გუნდს WinUI-ს კონკრეტული შესაძლებლობა სჭირდება. WPF გაუქმებული არ არის.

04WinForms

WinForms, Windows Forms, მაშინ ირჩევა, როცა ფანჯარა დღეს უნდა გავიდეს და გუნდს XAML არ სურს. ღილაკს დიზაინერში სვამ, მეთოდი კი იმ ღილაკის დაჭერაზე იწერება. წარწერის ტექსტს ის მეთოდი თვითონ ანიჭებს.

მზა კონტროლების ბაზარი აქ ისეთივე ძველია, როგორც თავად ფორმა. შიდა პროგრამა, რომელსაც რამდენიმე ადამიანი იყენებს, ხშირად სწორედ ასე იწყება. Visual Basic კვლავ სრულად იწერება. WinUI-ში და MAUI-ში Visual Basic არ გაქვს.

.NET 10-ში მუქი რეჟიმი ჩვეულებრივი API-ა, Application.SetColorMode. .NET 9-ში ის ჯერ საცდელი იყო და კომპილატორი გაფრთხილებას ითხოვდა. ახლა ის გაფრთხილება აღარ არის. რეჟიმს სვამ მანამ, სანამ პირველ ფორმას შექმნი. არჩევანია მუქი, ღია, ან სისტემის პარამეტრი.

საზღვარი მაინც დარჩა. მუქი რეჟიმი Windows 11-ზე ჩანს. კონტრასტულ თემაში ის ითიშება. თუ სისტემის რეჟიმს აირჩევ, Windows-ის თემის შეცვლა გახსნილ აპს თავისით არ გადაიყვანს, აპი თავიდან უნდა გაეშვას. ზოგი კონტროლი მუქ რეჟიმში უსწორმასწოროდ იხატება, რადგან ქვეშ Win32-ის კონტროლებია. Microsoft-ის დოკუმენტაცია ამ განსხვავებას ცნობილ შეზღუდვად წერს და მას შეცდომად არ აგდებს.

WinForms კონტროლს DirectX-ით არ ხატავს. კალამი და შეხება აქ სუსტად მუშაობს. Fluent-ის მასალები, Mica და Acrylic, აქ არ მოდის. იერი კლასიკურ Windows-ს ჰგავს მაშინაც, როცა ფონი მუქია.

თუ გუნდმა ეს ფორმა იცის და პროგრამას ის ჰყოფნის, Microsoft გადასვლას არ ითხოვს. ბოლო წლებში აქვე დაემატა ასინქრონული დიალოგი, მუქი რეჟიმი, მაღალი DPI და დიზაინერის გაუმჯობესება.

06MAUI

MAUI, .NET Multi-platform App UI, ერთი C# პროექტია ოთხი სისტემისთვის. Android, iOS, macOS Mac Catalyst-ით, და Windows. Linux ოფიციალურ სამიზნეში არ არის. ენა მხოლოდ C#-ია. Visual Basic, F# და C++ აქ არ იწერება.

ეკრანი შეიძლება იყოს XAML, ან C# კოდში აღწერილი განლაგება. ვინც Flutter-იდან მოდის, MAUI-ში ცალკე მოდელსაც ნახავს, სადაც ეკრანი მდგომარეობიდან თავიდან იგება. XAML თუ იცი, MAUI-ს ეკრანი სწრაფად იკითხება.

Windows-ზე აწყობილი MAUI აპის ფანჯარა WinUI 3-ია. დანარჩენ სამ სისტემაზე handler ერთ MAUI კონტროლს იმ სისტემის კონტროლზე რუკავს. ღილაკი Android-ზე Android-ის ღილაკია, iOS-ზე კი iOS-ის. ამიტომ აპს შეუძლია იმ სისტემის იერი მიიღოს, სადაც გახსნილია. საერთო API საკმარისია ფაილის, ქსელის და სენსორის ჩვეულებრივი საქმისთვის. კამერა, გაზიარების ფანჯარა ან სისტემის დიალოგი ხშირად მაინც ითხოვს პატარა ფაილს კონკრეტული სისტემისთვის. ასეთი ფაილი MAUI-ში ჩვეულებრივია.

აწყობა შეიძლება Visual Studio-ში Windows-ზე, ან VS Code-ში Windows-ზე და Mac-ზე. შაბლონი ცალკე workload-ია. dotnet new console მას არ ქმნის. ამ კვირის გვერდი იმ workload-ს არ აყენებს.

თუ დღეს მხოლოდ Windows გინდა და მოგვიანებით ტელეფონიც შეიძლება დაგჭირდეს, Microsoft ამბობს, რომ WinUI 3-იდან MAUI-ში გადმოსვლა მზა გზა არ არის. ასეთი გუნდი თავიდანვე MAUI-ზე იწყებს. თუ მომხმარებელი მხოლოდ Windows-ზე რჩება, პირდაპირი WinUI 3 აპი საკმარისია.

07Uno და Avalonia

MAUI-ს სიის გარეთ Linux დგას. იქ ორი .NET ფრეიმვორკი შედის, და ორივეს თავისი XAML აქვს.

Uno Platform WinUI-ს XAML-ს სხვა სისტემაზე მიჰყავს. სამიზნე არის Windows, macOS, Linux, iOS, Android და ბრაუზერი WebAssembly-ით. ეკრანი სისტემიდან სისტემაზე ერთნაირი რჩება. ეს არის გზა, როცა გუნდს WinUI უკვე დაწერილი აქვს და მერე Linux ან ვები დაემატა.

Avalonia WPF-ს უფრო ჰგავს, ვიდრე WinUI-ს. ისიც გადის Windows-ზე, macOS-ზე, Linux-ზე, ტელეფონზე და ბრაუზერში. კონტროლს ყველგან თავად ხატავს, Skia-თი. სურათი სისტემიდან სისტემაზე ერთნაირი რჩება. გუნდი, რომელმაც WPF იცის, აქ უფრო ადვილად შედის, ვიდრე Uno-ში.

ორივე Microsoft Store-ში გამოსაქვეყნებლად ვარგისია, ისევე როგორც WinUI, WPF, WinForms და MAUI. არჩევანის წინ კითხვა ერთია. ის API, რომელიც აპს სჭირდება, ამ ფრეიმვორკში საერთოდ არის თუ არა. თუ არ არის, ჯობს დარჩე WinUI-ზე, WPF-ზე ან WinForms-ზე, თუნდაც მეორე სისტემა გენდომებოდეს.

08React Native, PWA და Blazor

აქამდე ენა C# იყო. ზოგი გუნდი ფანჯარას JavaScript-ით წერს, და Windows ამასაც იღებს.

React Native Meta-ს ფრეიმვორკია. Facebook და Instagram ამ მოდელზე დგას. კომპონენტი და hook Windows-ზე React Native for Windows-ით მოდის, Mac-ზე კი React Native for macOS-ით. ეკრანი ადგილობრივ კონტროლად იხატება. Windows developer FAQ ვებგუნდს სწორედ აქ გზავნის, როცა დესკტოპის პროგრამა სჭირდებათ და React უკვე იციან.

PWA, Progressive Web App, საიტია, რომელიც აპივით ყენდება. ენა არის HTML, CSS და JavaScript. React, Vue, Angular ან ჩვეულებრივი JavaScript, რომელსაც გუნდი უკვე წერს. Edge-დან დაყენებული PWA იღებს ფანჯარას, Start მენიუს ხატულას, ფაილურ სისტემას, სათაურის ზოლს, მალსახმობს და კალამს. Microsoft Store ამ აპსაც იღებს.

Blazor Hybrid მაშინ გამოდგება, როცა ეკრანი უკვე ვებზეა დაწერილი და ფანჯარა .NET-ზე გინდა. Blazor-ის გვერდი შედის MAUI-ს აპში, და ასევე WPF-სა და WinForms-ში, თუ პროექტი თანამედროვე .NET-ზეა. .NET Framework-ის ძველი WPF და WinForms ამ ჰოსტს არ იღებს. .NET 9-იდან HybridWebView Blazor-ის გარდა სხვა JavaScript ეკრანსაც სვამს, მათ შორის Angular-ს, React-ს და Vue-ს. C# და JavaScript ერთმანეთს იძახებს. ერთი ეკრანი შეიძლება MAUI-ს კონტროლი იყოს, მეზობელი კი ვების გვერდი.

09რომელს ირჩევთ

ერთი სწორი პასუხი არ არის. ოთხი კითხვა სიას ამოკლებს.

  1. ყველა მომხმარებელი Windows-ზეა? თუ კი, სია არის WinUI 3, WPF და WinForms. თუ ტელეფონი, Mac ან Linuxაც გინდა, ჯერ შეამოწმე, საჭირო API არის თუ არა MAUI-ში, Uno-ში, Avalonia-ში ან React Native-ში. დაკარგული API გიბრუნებს Windows-ის სამ ფრეიმვორკთან.
  2. ვინ იყენებს და როდის უნდა გავიდეს? რამდენიმე ადამიანი და ხვალინდელი ვადა WinForms-ს ერგება, მით უმეტეს თუ გუნდი Visual Basic-ს წერს. საჯარო აპი, რომელსაც დღევანდელი Windows-ის იერი უნდა, WinUI 3-ს ერგება. WPF ერგება მაშინ, როცა კოდი უკვე WPF-აა, ან კონტროლი ჯერ მხოლოდ იქ იყიდება.

  4. გჭირდება Windows-ის API, რომელსაც ნატიური ფრეიმვორკი კარგად ხსნის? მაშინ WinUI, WPF და WinForms არჩევანში რჩება მაშინაც, როცა მეორე სისტემაც გინდა.

ბიზნესის პროგრამებში გუნდი ხშირად იმ ენას ირჩევს, რომელსაც უკვე წერს. დოკუმენტაციაც ასე ამბობს.
