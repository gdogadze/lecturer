არქიტექტურული შაბლონები და SOLID პრინციპები. MVC, MVVM და Clean Architecture-ის კონცეფციები, Dependency Injection და IoC კონტეინერების გამოყენება.

01ხუთი პრინციპი

SOLID ხუთი წესია. თითო ასოს ქვემოთ აქვს სრული სახელი, რას ნიშნავს, და კოდი. ჯერ კოდზე თქვით, რა არის ცუდი. „ასე არა“ ამ ახსნას ხსნის. შემდეგ იგივე ამოცანა წესის დაცვითაა.

SRP. Single Responsibility Principle

SRP = Single Responsibility Principle. ერთი პასუხისმგებლობის პრინციპი.

ერთად შეკრიბე ის, რაც ერთი მიზეზით იცვლება, და ერთმანეთისგან დააშორე ის, რაც სხვა მიზეზით იცვლება. წესი მეთოდების რაოდენობას არ ითვლის. წესი ცვლილების მიზეზს ითვლის.

public static int Sum(int[] scores)
{
    int total = 0;
    foreach (int score in scores)
    {
        total += score;
        Console.WriteLine($"Added {score}, running total = {total}");
    }
    return total;
}

ასე არა. ერთი მეთოდი ჯამსაც ითვლის და ყოველ ნაბიჯზე ეკრანზეც ბეჭდავს.

ასე. ჯამი ბიბლიოთეკაში რჩება. ბეჭდვა იქ ხდება, სადაც პროგრამა იწყება.

public static class Grades
{
    public static int Sum(int[] scores)
    {
        int total = 0;
        foreach (int score in scores)
            total += score;
        return total;
    }
}

// Program.cs
int[] scores = [10, 9, 8];
int total = Grades.Sum(scores);
Console.WriteLine(total);

ცუდი მეთოდი ორი მიზეზით იცვლება: ან ჯამის წესი შეიცვლება, ან ტექსტი, რომელსაც ადამიანი კითხულობს. ამიტომ გამოთვლა და ეკრანი გაიყო. Microsoft იგივე აზრს ფენებზეც ავრცელებს: ბიზნესის წესი, მონაცემთა შენახვა და ეკრანი ცალ-ცალკე პროექტებშია.

Solid Relevance. Microsoft-ის ფორმულირება: Architectural principles.

SRP ამ კლასისგან რას მოითხოვს?

OCP. Open-Closed Principle

OCP = Open-Closed Principle. ღია-დახურული პრინციპი.

მოდული ღიაა გაფართოებისთვის და დახურულია იმ კოდის რედაქტირებისთვის, რომელიც უკვე სწორად მუშაობს. ახალი ქცევა ახალი ტიპია. უკვე სწორ მეთოდში ახალი ტოტი არ ემატება.

public static int Average(int[] scores, string mode)
{
    if (scores.Length == 0)
        return 0;

    int total = 0;
    foreach (int score in scores)
        total += score;

    int raw = total / scores.Length;
    if (mode == "up" && total % scores.Length != 0)
        return raw + 1;
    return raw;
}

ასე არა. დამრგვალების ყოველი ახალი წესი Average-ის შიგნით ახალ if-ს ამატებს.

ასე. თითო წესი საკუთარი კლასია. Average მხოლოდ ჯამს სთხოვს დამრგვალებას.

public interface IRounder
{
    int Round(int total, int count);
}

public class FloorRounder : IRounder
{
    public int Round(int total, int count)
    {
        if (count == 0)
            return 0;
        return total / count;
    }
}

public class CeilingRounder : IRounder
{
    public int Round(int total, int count)
    {
        if (count == 0)
            return 0;
        if (total % count == 0)
            return total / count;
        return total / count + 1;
    }
}

public static int Average(int[] scores, IRounder rounder)
{
    int total = 0;
    foreach (int score in scores)
        total += score;
    return rounder.Round(total, scores.Length);
}

ცუდ კოდში მესამე წესი, მაგალითად უახლოეს მთელამდე, კვლავ Average-ის რედაქტირებას მოითხოვდა. ახლა ის ახალი კლასია, IRounder-ის კიდევ ერთი რეალიზაცია. FloorRounder და Average უცვლელი რჩება. დღევანდელ ლაბორატორიაში ეს ინტერფეისი არ გვჭირდება: საშუალო მთელ რიცხვზე იყოფა, როგორც FloorRounder.

LSP. Liskov Substitution Principle

LSP = Liskov Substitution Principle. ლისკოვის ჩანაცვლების პრინციპი.

ინტერფეისის რეალიზაციამ არ უნდა დააბნიოს ის კოდი, რომელიც ამ ინტერფეისს იყენებს. Add-ით შენახული ქულა All-ში უნდა დაბრუნდეს.

public interface IGradeStore
{
    void Add(int score);
    int[] All();
}

public class EvenDroppingStore : IGradeStore
{
    private readonly List<int> _scores = [];

    public void Add(int score)
    {
        if (score % 2 != 0)
            _scores.Add(score);
    }

    public int[] All()
    {
        return [.. _scores];
    }
}

ასე არა. მაღაზია ლუწ ქულებს აგდებს. საშუალოს გამოთვლა ამას ვერ ხედავს და არასწორ რიცხვს იღებს.

ასე. მაღაზია ინახავს ყველა ქულას, რომელსაც Add იღებს.

public class MemoryGradeStore : IGradeStore
{
    private readonly List<int> _scores = [];

    public void Add(int score)
    {
        _scores.Add(score);
    }

    public int[] All()
    {
        return [.. _scores];
    }
}

10, 7 და 8 ჯამში 25-ია. 25 გაყოფილი 3-ზე მთელ რიცხვებში 8-ია. EvenDroppingStore 10-სა და 8-ს აგდებს, რჩება 7, და საშუალო 7 ხდება. MemoryGradeStore სამივეს აბრუნებს, ამიტომ საშუალო 8 რჩება. სერვისის კოდი არ შეცვლილა. შეიცვალა მაღაზია, რომელიც ინტერფეისის დაპირებას არღვევდა.

ISP. Interface Segregation Principle

ISP = Interface Segregation Principle. ინტერფეისის გამიჯვნის პრინციპი.

ინტერფეისი პატარა უნდა იყოს, რომ მომხმარებელი იმ მეთოდზე არ იყოს დამოკიდებული, რომელსაც არ იძახებს.

public interface IGradeStore
{
    void Add(int score);
    int[] All();
    void Print(int average);
}

public class MemoryGradeStore : IGradeStore
{
    private readonly List<int> _scores = [];

    public void Add(int score)
    {
        _scores.Add(score);
    }

    public int[] All()
    {
        return [.. _scores];
    }

    public void Print(int average)
    {
        Console.WriteLine(average);
    }
}

ასე არა. შენახვის ინტერფეისში ბეჭდვაც დევს. მაღაზია იძულებულია Print დაწეროს, თუმცა ეკრანს არ ემსახურება.

ასე. შენახვას თავისი ინტერფეისი აქვს. ეკრანს საკუთარი ტიპი.

public interface IGradeStore
{
    void Add(int score);
    int[] All();
}

public class ConsoleGradePrinter
{

    {
        Console.WriteLine(average);
    }

GradingService მხოლოდ Add-სა და All-ს იძახებს. ცუდ ინტერფეისზე ის მაინც Print-ზე იყო დამოკიდებული, რადგან ეს მეთოდი კონტრაქტში იდგა. ბეჭდვა ცალკე ტიპში გადავიდა. დღეს ლაბორატორიაში ეს ტიპი არ იწერება: ერთ სტრიქონს Program.cs ბეჭდავს.

DIP. Dependency Inversion Principle

DIP = Dependency Inversion Principle. დამოკიდებულების ინვერსიის პრინციპი.

მაღალი დონის კოდი დაბალი დონის დეტალზე არ უნდა იყოს დამოკიდებული. ორივე აბსტრაქციაზე უნდა იყოს დამოკიდებული. აქ მაღალი დონე საშუალოს გამოთვლის წესია. დაბალი დონე კლასია, რომელიც ქულებს სიაში ინახავს.

public class GradingService
{
    private readonly MemoryGradeStore _store = new MemoryGradeStore();

    public void Add(int score)
    {
        _store.Add(score);
    }

    public int Average()
    {
        int[] scores = _store.All();
        if (scores.Length == 0)
            return 0;

        int total = 0;
        foreach (int score in scores)
            total += score;

        return total / scores.Length;
    }
}

ასე არა. სერვისი კონკრეტულ მაღაზიას თვითონ ქმნის. სხვა მაღაზიის ჩასასმელად ამ ფაილის რედაქტირებაა საჭირო.

ასე. სერვისი მხოლოდ ინტერფეისს იცნობს. კონკრეტული მაღაზია გარედან მოდის. ეს სამი ტიპი ლაბორატორიის ბიბლიოთეკაა.

ინტერფეისი ის სახელია, რომლითაც სერვისს შენახვის მოთხოვნა შეუძლია. პირველადი კონსტრუქტორი პირველი კვირიდან გვახსოვს: პარამეტრი ტიპის სახელთან ერთად კონსტრუქტორში იწერება. მეთოდი ამ პარამეტრს უშუალოდ იყენებს.

{

ცუდ კოდში სერვისი MemoryGradeStore-ს სახელს იცნობდა და თვითონ ქმნიდა. ტესტი სხვა მაღაზიას ვერ ჩასვამდა ამ ფაილის რედაქტირების გარეშე. კონსტრუქტორის პარამეტრი ამ რედაქტირებას ხსნის: სერვისი მხოლოდ IGradeStore-ს იცნობს, კონკრეტული მაღაზია კი ტესტში ან Program.cs-ში იქმნება.

საშუალო მთელი რიცხვია, ქულის მსგავსად. 10, 9 და 8 ჯამში 27-ს იძლევა, 27 გაყოფილი 3-ზე კი 9-ია. ცარიელი მაღაზია 0-ს აბრუნებს, რადგან ჩვენ ასე დავწერეთ. ეს მათემატიკის კანონი არ არის.

02სამი შაბლონი

MVC, MVVM და Clean Architecture ერთი იდეის სამი სახელია. წესი შიგნით რჩება. ეკრანი, ფაილი და კონტეინერი გარეთ. თითო შაბლონს ქვემოთ აქვს კოდი. ჯერ კოდზე თქვით, რა არის ცუდი. „ასე არა“ ამ ახსნას ხსნის. შემდეგ იგივე ამოცანა წესის დაცვითაა.

MVC. Model-View-Controller

MVC = Model-View-Controller. მოდელი-ხედი-კონტროლერი.

მოდელი ინახავს მდგომარეობას და წესს. ხედი აჩვენებს. კონტროლერი მოდელს ეძახის და ხედს ირჩევს. მოდელმა ეკრანი არ უნდა იცოდეს. ASP.NET Core MVC-ში ხედიც და კონტროლერიც მოდელზეა დამოკიდებული. დღეს ვებსაიტს არ ვქმნით. კონსოლში Program.cs კონტროლერი და ხედი ერთადაა: სერვისს სთხოვს რიცხვს და ბეჭდავს.

public class GradingService(IGradeStore store)
{
    public void Add(int score) => store.Add(score);

    public int Average()
    {
        int[] scores = store.All();
        if (scores.Length == 0)
            return 0;
        int total = 0;
        foreach (int score in scores)
            total += score;
        return total / scores.Length;
    }

    public void Report()
    {
        Console.WriteLine(Average());
    }
}

ასე არა. მოდელი ეკრანზე თვითონ ბეჭდავს. ხედის შეცვლა, მაგალითად ვებგვერდით, მოდელის ფაილსაც შეცვლის.

ასე. მოდელი მხოლოდ რიცხვს აბრუნებს. ბეჭდვა Program.cs-ში რჩება.

Overview of ASP.NET Core MVC.

MVC-ში რომელი კომპონენტია დამოკიდებული მოდელზე?

MVVM. Model-View-ViewModel

MVVM = Model-View-ViewModel. მოდელი-ხედი-ხედის მოდელი.

მოდელი ისევ წესია. ხედი ფანჯარაა, მომავალ კვირაში XAML. ViewModel მათ შორის დგას: ხედს აწვდის იმას, რასაც ეკრანი აჩვენებს, და მოდელს ეძახის. ხედმა ViewModel იცის. ViewModel-მა ხედი, ღილაკი და Console არ უნდა იცოდეს.

// Program.cs პირდაპირ მოდელს ეძახის და ტექსტსაც თვითონ წყვიტავს
var grading = new GradingService(new MemoryGradeStore());
grading.Add(10);
grading.Add(9);
grading.Add(8);
int avg = grading.Average();
Console.WriteLine($"საშუალო: {avg} ქულა");

ასე არა. ხედი მოდელს პირდაპირ ეძახის და პრეზენტაციის წესსაც ინახავს. ფანჯრის შეცვლა ამ ფაილსაც შეცვლის.

ასე. ViewModel მოდელს ფარავს. ხედი მხოლოდ ViewModel-ის ველებს კითხულობს.

public class GradeViewModel(GradingService grading)

      თუ რეგისტრაცია გაეშვა, მაგრამ საშუალო მაინც უცნაურია, ტესტის წითელი ტექსტი თან წაიღეთ და კითხვა r/dotnet-ზე დასვით. რეგისტრაციის კოდის გარეშე დასმულ კითხვას პასუხი არ მოჰყვება.
